# 01 · 现有检测器行为分析

> 本文档回答一个问题：**RhyDive 现在的音符检测器，为什么会在"密集 32 分钢琴"和
> "变化不大的连奏人声"上漏检？**
>
> 结论先行：这不是"调参没调好"，而是两个**结构性**限制，分别落在**时间轴**和**音高轴**上。

---

## 0. 分析方法与免责声明

- 本文档描述的行为，是在 **RhyDive 0.6.15** 上观察得到的。
- 描述方式为**行为观察 + 独立重述**：下面的伪代码是本文档作者按观察结果重新写的，
  **不是** 原项目代码，也不应被当作原项目代码来读。
- 本仓库不包含、不依赖 RhyDive 的任何代码或资源。
- 本文档的目的是**说明问题**，不是在评判实现质量。就它面向的场景而言，
  这套检测器是一个合理的工程选择，只是在两个特定素材上碰到了设计边界。

---

## 1. 这条链路在哪里

RhyDive 的客户端里有一条**直接从音频检测音符**的链路（Dive 玩法）。它的处理顺序是：

~~~text
音频文件（URL）
  → 取回并解码为 PCM
  → 混成单声道
  → 谱通量起音检测          ← 本文分析的对象
  → 把检测到的起音对齐到谱面音符时钟
  → 按「音频指纹 + 谱面」缓存结果
~~~

几个对后续设计有影响的观察：

- **全离线**：整首歌先解码成 PCM 再一次性分析，不是流式。
- **跑在 renderer 的 Worker 里**，用的是 Web Audio 的解码能力。
- **结果会缓存**，所以"算得慢一点"是可接受的代价。

## 2. 观察到的算法

### 2.1 总览

它是一条**单分辨率谱通量（spectral flux）**检测器，外加一套自适应阈值和峰值挑选：

~~~text
分帧 → 加窗 → FFT → 对数频带聚合 → 谱通量 → 自适应阈值 → 峰值挑选
                                        → 音区合并 → 与谱面对齐
~~~

### 2.2 分帧与加窗

- **帧移**：10 ms（即 100 帧/秒）
- **分析窗**：约 23 ms，取最接近的 2 的幂（44.1 kHz 下为 1024 点），Hann 窗

帧移 10 ms 意味着时间轴的理论分辨率是 10 ms。**这一点很重要，因为后面真正的瓶颈
不在帧移，而在输出层的合并规则。**

### 2.3 对数频带聚合

对每一帧的 FFT 幅度谱，按 **24 个对数等分频带**从 **55 Hz 到 10 kHz** 聚合能量：

~~~text
bandMag[b] = Σ |spectrum[k]|              for k in band b
bandMag[b] = log1p( 40 * bandMag[b] / binCount(b) / (win/4) )
~~~

注意 `log1p` 压缩：它对**弱信号更友好**（近似对数，小的变化也能体现），
这是它能在安静段落工作的一部分原因。但要注意——**它压缩的是幅度，不是频率**。

24 个频带覆盖 55 Hz–10 kHz（约 7.5 个八度），所以：

> **每个频带平均宽约 3.75 个半音。**

这个数字后面会反复用到。它意味着**这条链路的频率分辨率大约只有 3/4 个全音**，
无法分辨半音级的音高变化。

### 2.4 三个音区

24 个频带被归入 3 个"音区"：

| 音区 | 频率范围 | 大致对应 |
|---|---|---|
| 低 | 55 – 180 Hz | 贝斯、低音区 |
| 中 | 180 – 2500 Hz | 人声与大部分乐器的基频区 |
| 高 | 2500 – 10000 Hz | 泛音、打击乐、齿音 |

每个音区**独立走一遍后面的阈值与峰值挑选**，最后再合并。

### 2.5 谱通量

~~~text
flux[f] = Σ_b max(0, bandMag[f][b] - bandMag[f-2][b])
~~~

- 对照的是 **2 帧前（20 ms）**，不是前一帧
- **只取正增量**（半波整流），这是标准做法

同时，每个音区也单独累加自己那部分的正增量，得到**每音区的新颖度曲线**。

### 2.6 自适应阈值

对通量曲线做"减去局部均值"再做分位数归一化：

~~~text
localMean[i] = 通量在 [i-500ms, i+500ms] 内的滑动平均
env[i] = max(0, flux[i] - localMean[i])
a = env 中所有正值的 0.9 分位数
if a < 1:  env 全部置 0        # 全局灵敏度闸门
else:      env[i] = min(2, env[i] / a)
~~~

这里有三个对失效分析很关键的机制：

1. **±500 ms 的局部均值扣除**：任何在 1 秒尺度内缓慢变化的能量，都会被减掉。
2. **0.9 分位数归一化**：把曲线拉到同一量级，但也会让**弱事件被强事件压制**。
3. **分位数低于 1 就整体清零**：这是一个全局闸门，安静段落会整体返回空。

### 2.7 峰值挑选

在归一化后的包络上找局部极大值：

~~~text
for i in 3 .. len-3:
    if env[i] < 0.15: continue
    if env[i] 不是 [i-3, i+3] 内的严格最大值: continue
    用相邻三点做抛物线插值，细化到亚帧精度
    strength = min(1, env[i])
    if 与上一个已保留的 onset 相距 < 55 ms:
        保留两者中较强的那个        # ← 关键
    else:
        保留为新的 onset
~~~

### 2.8 音区合并

三个音区的 onset 列表合并：

~~~text
把所有音区的 onset 按时间排序（同一时刻强的在前）
若当前 onset 与上一个已保留的相距 < 30 ms:
    保留较强的那个
~~~

### 2.9 与谱面对齐

检测出的 onset 不会直接使用，而是先和谱面的音符时钟做**全局滞后对齐**：

~~~text
在 lag ∈ [-90 ms, +90 ms] 内以 2 ms 步长搜索：
    score(lag) = Σ 所有谱面音符时刻处的包络插值值(音符时刻 + lag)
取 score 最大的 lag
confidence = 最佳得分 / 所有 lag 的平均得分
if confidence < 1.5:
    标记为"不可用"
最终 onset 时刻 = 检测时刻 - lag
~~~

置信度的定义（峰值 / 均值）值得注意：它衡量的是
"**在谱面音符位置，包络是否比平均值明显更集中**"。
信噪比不够高就直接判定这条分析不可用。

### 2.10 缓存

分析结果按 **音频文件指纹（ETag / Last-Modified / Content-Length）**
+ **谱面音符时间的哈希** 作为键缓存，换一首歌或改一次谱面都会失效重算。

## 4. 失效分析一：密集 32 分钢琴 —— **时间轴被限死**

### 4.1 先算一下 32 分有多密

| BPM | 一拍 | 16 分 | **32 分** |
|---|---|---|---|
| 120 | 500 ms | 125 ms | **62.5 ms** |
| 140 | 428.6 ms | 107.1 ms | **53.6 ms** |
| 160 | 375 ms | 93.75 ms | **46.9 ms** |
| 180 | 333.3 ms | 83.3 ms | **41.7 ms** |
| 200 | 300 ms | 75 ms | **37.5 ms** |

只要 BPM 高于约 **136**，32 分音符的间隔就短于 55 ms。

### 4.2 三道闸门，任何一道都足以致命

| 机制 | 位置 | 对 32 分的影响 |
|---|---|---|
| **局部极大窗口 ±30 ms** | 峰值挑选 | 两个候选若相距 < 30 ms，弱的那一个**不是局部极大**，直接被判为非峰值 |
| **同音区最小间距 55 ms** | 峰值挑选 | 相距 < 55 ms 的 onset **被合并**，只留较强的 |
| **跨音区合并 30 ms** | 音区合并 | 即使两个 onset 落在不同音区，相距 < 30 ms 也会被合并 |

所以：

> **在 160 BPM 下，32 分音符间隔 46.9 ms。它同时低于 55 ms 的最小间距，
> 也接近 30 ms 的局部极大窗口。检测器在输出层就被禁止产生这两个音符。**

这不是"检测得不够准"，而是**输出层的合并规则从结构上禁止了它**。
10 ms 的帧移本来完全有能力分辨 46.9 ms，但这份能力在最后一步被丢掉了。

### 4.3 为什么会这样设计

这个 55 ms 的设定是**合理的工程选择**：它防的是"同一个音符被重复检出一堆 onset"
以及"颤音、抖弓造成的误报"。对一般的流行曲、4 分/8 分节奏，它工作得很好。

问题只在于：它把"最小音符间隔"**硬编码成了一个与 BPM 无关的常量**。
一旦素材里出现比 55 ms 更密的音型，就没有任何参数能救。

## 5. 失效分析二：变化不大的连奏人声 —— **音高轴没有被观测**

先明确一件事：

> **这套检测器观测的是"能量变化"，而不是"音高"。**

它对一个声音事件的判据是"某一帧的能量相对 20 ms 前在某些频带上增加了"。
对**有瞬态**的声音（鼓、钢琴起音、辅音），这非常有效。
但连奏的人声换音，**根本没有瞬态**——它是基频平滑地滑到新位置，能量几乎连续。

### 5.1 四重压制

| 机制 | 效果 |
|---|---|
| **±500 ms 局部均值扣除** | 缓慢变化的能量被整体减掉，不留残余 |
| **0.9 分位数归一化** | 弱事件被同段落里的强事件压制；安静段落里的换音会低于阈值 |
| **峰值幅度下限 0.15** | 弱事件直接出局 |
| **全局灵敏度闸门** | 整段能量偏低时，直接返回空 |

### 5.2 更根本的问题：频率分辨率

即使能量上能看见，它也**分辨不出音高变了**：

- 分析窗固定 ≈ 23 ms → 频率分辨率 ≈ 43 Hz
- 在 1 kHz 处，43 Hz ≈ **73 音分**，比一个半音（100 音分）还宽
- 而 24 个频带平均宽 **3.75 个半音**

也就是说：

> **它看不见"音高从 C 走到了 D"，只能看见"能量炸了一下"。**
> 对于没有"炸"的连奏人声，就没有任何信号可依据。

### 5.3 小结

| 症状 | 观测轴 | 结论 |
|---|---|---|
| 32 分钢琴漏检 | **时间轴** | 有能力分辨，但在输出层被合并规则禁止 |
| 弱人声漏检 | **音高轴** | 根本没有观测音高，无从判别 |

**这是两个不同轴上的问题。** 这一点决定了改进方案的形状——见
[docs/02-design.md](02-design.md) 的"被否决的方案"。

---

## 6. 一个顺带发现：每音区的新颖度曲线已经算出来了

算法在累加总通量的同时，**也分别算出了三个音区各自的通量曲线**
（见 2.5 节），但观察到的调用方**只使用它们做音区合并，没有把它们用于判定**。

这意味着：**"按音区分别判定"这个钩子已经存在，只是没被用起来。**
一个自然的改进方向是——用它来做**多分辨率**或**音区相关的差异化策略**
（例如低频用更长的持续性判据、高频用更短的），而不必重写整条链路。

---

## 7. 更大的落差：官方曲目 vs 用户曲目

RhyDive 自带的曲目是带谱面的，而且看得出经过一套相当讲究的离线制作流程
（节奏 token → 乐句 → 意图 → 演出编排 → 空间调度）。
用户自己导入或上传的歌，则只能依赖第 1 节这条**客户端检测链路**。

也就是说：

> **同一款游戏里，"官方内容的谱面质量"和"用户内容的谱面质量"
> 由两套完全不同量级的管线决定。**

这是本仓库存在的另一个理由：**用户的歌也值得被认真对待。**

---

## 8. 结论：对改进方案的硬性约束

从上面的分析可以导出三条约束，后续设计必须满足：

1. **必须能输出间隔 < 55 ms 的独立事件。**
   这是 32 分问题的直接解药，也意味着要放弃"固定最小间距"这种与 BPM 无关的常量。
   （帧移 10 ms 已经够用，问题在输出层。）

2. **必须引入一个观测音高的通道。**
   纯能量类特征在连奏人声上无解，无论怎么调参。

3. **但频率分辨率不能盲目提高。**
   把频带做细会同时放大**颤音**造成的误报——这是本项目最大的陷阱，
   推导见 [docs/02-design.md](02-design.md) 第 2 节。

第 3 条是最容易被忽略的一条：**"漏检"和"误报"在这里是一枚硬币的两面**，
而颤音就是那枚硬币的边缘。
